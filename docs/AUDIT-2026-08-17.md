# Project Audit — Bagh-e-Kabul (`afghan-cyrine`)

**Date:** 17 August 2026
**Commit audited:** `e140542` — *Fix: don't throw on missing DATABASE_URL at module load*
**Lens for this audit:** *get it production-ready.* Findings are ranked by what
stands between this codebase and safely serving a real restaurant's real orders,
not by abstract code cleanliness.

**Method:** static read of the full source tree (154 files under `src/`,
`prisma/`, `scripts/`, plus all infra config). No production system, no live
database, no traffic data, and no running instance were available — every claim
below is traceable to a file and line, and anything I could not prove is marked
as an **assumption to validate** rather than stated as fact. `npm audit` could
not run (no registry egress from the audit environment), so dependency CVE
exposure is explicitly unassessed.

---

## 1. Executive summary

Bagh-e-Kabul is a single-restaurant ordering platform — public menu, delivery /
pickup / QR-code dine-in ordering, Stripe checkout, live order tracking, and an
owner-facing admin panel — with an unusual differentiator: AI-generated AR
models that let a customer see a dish at true physical size on their own table.

**The code is well above the quality bar for its stage.** The invariants that
matter for money and for the kitchen are enforced in the right layer and
documented with the reasoning behind them: prices are always re-derived
server-side (`src/lib/orders.ts:67-82`), the Stripe webhook is genuinely
idempotent and refuses to resurrect a cancelled order
(`src/lib/order-payments.ts:45-56`), the order state machine is a real state
machine (`src/lib/order-state.ts`), and public tracking serves an explicit
allow-list projection rather than a filtered row
(`src/lib/order-tracking.ts:18-36`). Several classes of bug that normally reach
production here have already been found and fixed.

**What's missing is not code quality — it's operations.** There is not a single
automated test in the repository. There is no error monitoring, no log
aggregation, and no alerting. There is no automated database backup. The
business details the site displays are still the scaffold's placeholders, and
the development `.env` still carries the default admin password. The result is a
system that is written like early-production software but *operated* like a
prototype: if the Stripe webhook starts failing at 7pm on a Friday, nothing in
this stack will tell anyone.

**Headline verdict:** a strong late-MVP that is roughly two weeks of unglamorous
work away from being genuinely safe to run a restaurant on. None of the top four
blockers are architectural — they are all things the project simply does not have
yet.

## 2. Business Context Brief

### Objective and value proposition

The product replaces three things a small independent restaurant would otherwise
pay for separately: a marketplace listing, a QR-menu tool, and an order-taking
system. A diner scans the code on their table and orders from their own phone
without installing anything; a delivery or pickup customer orders from the same
menu; the owner watches all of it arrive on one screen that updates itself
(`src/app/api/admin/orders/stream/route.ts`). The economics are the point — every
order is first-party, so the restaurant keeps the whole ticket instead of the
15–30% third-party marketplaces charge ([Rezku](https://rezku.com/blog/third-party-delivery-fees-in-2026-what-doordash-uber-eats-grubhub-really-cost-restaurants/),
[Orderitto](https://orderitto.com/blog/how-much-does-doordash-charge-restaurants)).

The AR feature is the genuine differentiator and it is not a gimmick as built.
The whole pipeline exists to answer "how big is this dish, really" — models are
generated at a real-world size derived from the dish's category, verified after
download, and corrected if wrong (`src/lib/ar-scale.ts`, `src/lib/glb.ts`,
`src/lib/ar-generation.ts:48-70`). Portion-size uncertainty is a real reason
people don't order unfamiliar cuisine, and this is a credible attack on it.

### Market positioning

The category is commission-free direct restaurant ordering, where the
alternatives are (a) Uber Eats / DoorDash — reach, at 15–30% of every order; (b)
POS-bundled ordering from Toast, Square or TouchBistro — cheaper per order but
tied to the POS contract ([TouchBistro](https://www.touchbistro.com/blog/best-pos-for-commission-free-online-ordering/),
[Owner.com](https://www.owner.com/blog/online-ordering-system-for-restaurants));
(c) a template site plus a QR-menu SaaS; and (d) doing nothing and taking phone
orders. Against all of them the differentiators are AR portion preview and full
ownership of the stack. Against all of them the weakness is the same: no
demand-generation. A marketplace brings customers; this brings none, so it only
wins for a restaurant that already has footfall and wants to stop renting its own
customers back.

**Assumption to validate:** the seed data is drawn from a Washington DC
restaurant's public menu (`prisma/seed.ts:17-18`), prices are in USD
(`src/lib/constants.ts:26`, `src/lib/utils.ts:8-13`), and the placeholder address
is San Francisco — but the project's own audit documentation is written in French
and the restaurant's name is bilingual ("Le Jardin de Kaboul"). If the real
restaurant is in Europe, currency, price formatting and VAT handling are all
wrong today and this becomes a money bug rather than a cosmetic one.

### Maturity level: **late MVP, pre-launch** — with a split personality

Placed against concrete signals rather than vibe:

| Signal | Present? | Evidence |
| --- | --- | --- |
| Authentication | Yes | JWT session cookie, bcrypt, `src/lib/auth.ts` |
| Payments | Yes | Stripe Checkout + idempotent webhook + fallback reconciliation |
| Input validation | Yes, thorough | `src/lib/validators.ts`, per-route schemas, body-size caps |
| Rate limiting | Yes, two-stage | `src/lib/api-limits.ts` |
| Migrations | Yes | `prisma/migrations/`, `migrate deploy` in the entrypoint |
| CI | Partial | `.github/workflows/ci.yml` — typecheck, lint, build, docker build |
| Containerised deploy + TLS automation | Yes | `docker-compose.yml`, certbot + nginx reload loop |
| **Automated tests** | **No** | zero test files in the repository |
| **Error monitoring / alerting** | **No** | 14 `console.error` calls; no Sentry, OTel, or log shipping |
| **Automated backups** | **No** | manual `pg_dump` documented in the README only |
| **Real business data** | **No** | `src/lib/constants.ts:7-23` is still scaffold placeholder |

The infrastructure and the domain logic are early-production grade. The
operational practice is prototype grade. That gap *is* the audit finding.

### End users vs. customer

They are different people and the code knows it. The **customer** — who decides
to run this — is the restaurant owner. The **end users** are diners, most of them
one-time, on phones, on restaurant WiFi, with no account.

The code shows unusually little bias toward the buyer at the user's expense.
Cash dine-in asks for no name, email, or phone at all
(`src/lib/validators.ts:168-173`) because the table is the identity — a decision
that costs the owner a marketing list and is right for the diner. Tracking works
with no sign-in, and completed orders are purged from the device
(`README.md` → "Order Tracking"). Where the balance does tilt, it tilts toward
the owner in the operational sense rather than the commercial one: the admin
panel gets live SSE updates and an audible alert, while the diner-facing
menu is the part with no caching and the largest payload (§4, finding 11).

## 3. Clean architecture breakdown — the target shape

The current architecture is already close to the right one. This is what it
should converge on, not a redesign:

```
┌─────────────────────────────────────────────────────────────┐
│  PRESENTATION                                               │
│  src/app/(site)/**     public pages (RSC)                   │
│  src/app/admin/**      admin pages (RSC, guarded by proxy)  │
│  src/components/**     dumb-ish view components             │
│  src/store/**          client-only state (cart, sessions)   │
└───────────────┬─────────────────────────────────────────────┘
                │ may call ↓ only
┌───────────────▼─────────────────────────────────────────────┐
│  HTTP BOUNDARY                                              │
│  src/app/api/**        parse → authenticate → rate-limit →  │
│                        delegate → serialise. No business    │
│                        rules of its own.                    │
│  src/lib/api-limits.ts, http.ts, auth.ts, proxy.ts          │
└───────────────┬─────────────────────────────────────────────┘
                │
┌───────────────▼─────────────────────────────────────────────┐
│  DOMAIN  (pure where possible, the part worth testing)      │
│  validators.ts   what a stranger may send                   │
│  orders.ts       re-pricing, availability, table validity   │
│  order-state.ts  legal status transitions          [pure]   │
│  order-payments.ts  idempotent Stripe reconciliation        │
│  order-tracking.ts  public projection + stages     [pure]   │
│  table-qr.ts     QR URL + param parsing            [pure]   │
│  ar-scale.ts     real-world dish sizing            [pure]   │
└───────────────┬─────────────────────────────────────────────┘
                │
┌───────────────▼─────────────────────────────────────────────┐
│  DATA + INTEGRATIONS                                        │
│  prisma.ts → Postgres  │  r2.ts/uploads.ts → Cloudflare R2  │
│  stripe.ts → Stripe    │  meshy.ts/glb.ts → Meshy AI        │
│  order-events.ts  in-process pub/sub (single-instance)      │
└─────────────────────────────────────────────────────────────┘
```

Two things about this shape are worth stating explicitly, because they are
choices rather than accidents:

**Server Components reading Prisma directly is correct here, not a layering
violation.** `src/app/(site)/menu/page.tsx:28-41` and the admin pages query the
database from the page. In the App Router the RSC *is* the controller; inserting
a service layer purely to satisfy a diagram would add indirection with no
consumer. The rule that matters is the one already being followed: **anything
that decides something goes in `src/lib/`, anything that only fetches and renders
can stay in the page.** The one place this leaks is query *shapes* being repeated
across pages — worth extracting only once a shape appears in a third file.

**The single-instance assumption is load-bearing and correctly documented.**
The rate limiter (`src/lib/rate-limit.ts:1-13`), the SSE bus
(`src/lib/order-events.ts:9-14`) and the AR generation lock
(`src/lib/ar-generation.ts:185`) are all per-process. Each says so, and says what
a multi-instance deployment would need instead. That is the right trade for one
restaurant. The consequence to accept consciously: **there is no zero-downtime
deploy and no horizontal scale.** Every release drops live order trackers and
resets rate-limit counters. For one restaurant, deploy between services and this
never matters — but it is a hard ceiling, not a soft one, and the moment a second
restaurant is onboarded, all three need a shared store.

## 4. Critical problem areas, ranked

### P0-1 — Zero automated tests, on a codebase whose entire design is invariant-driven

**Where:** no test files anywhere; `package.json` has no test script;
`.github/workflows/ci.yml` runs `tsc --noEmit`, `eslint`, `next build`, and a
docker build — nothing that executes a single business rule.

**Why it matters here specifically:** this codebase's value is concentrated in
rules that are invisible to the type checker. `cardOrderSchema` must reject
`DINE_IN` (`validators.ts:193-203`). `checkFulfillment` must reject a table
number on a delivery order (`validators.ts:137-143`). `markOrderPaid` must not
drag a `COMPLETED` order back to `CONFIRMED` (`order-payments.ts:53-56`).
`canTransition` must refuse `COMPLETED → PENDING` (`order-state.ts:44-45`).
Every one of these is a rule someone can silently break in a five-line refactor,
and `tsc` will pass, `eslint` will pass, the build will pass, and the first
signal will be a customer or the kitchen.

The README documents past incidents that all fit this pattern — a 50,000-item
order that locked the database for 22 seconds, an unauthenticated endpoint
returning customers' addresses, Stripe redirects baked to `localhost`. Each was
fixed. None has a regression test.

**Severity: P0.** This is the single highest-leverage gap in the project.

**Fix:** not "add tests" — add *these* tests, in this order (§6 has runnable
code):
1. Pure-function unit tests for `order-state.ts`, `order-tracking.ts`,
   `table-qr.ts`, `validators.ts`. No database, no mocks, fast. Covers most of
   the rules above.
2. Integration tests for `buildOrderFromCart` and `order-payments.ts` against a
   throwaway Postgres (the `docker-compose.dev.yml` container already exists).
3. One end-to-end happy path per fulfillment type.
4. Wire `npm test` into the existing CI job so it gates merges.

### P0-2 — No error monitoring, no log aggregation, no alerting

**Where:** 14 `console.error` / `console.info` calls, e.g.
`api/orders/route.ts:63`, `api/stripe/webhook/route.ts:90`,
`checkout/success/page.tsx:43`, `order-events.ts:79`. No `instrumentation.ts`, no
Sentry / OpenTelemetry / pino / log driver configured in `docker-compose.yml`.

**The concrete failure:** `src/app/api/stripe/webhook/route.ts:89-92` catches a
handler failure, logs it, and returns 500 so Stripe retries. That is exactly
right — but the log goes to the container's stdout, which nobody reads, and
Stripe gives up after three days. A customer's card is charged and the order is
never marked paid; the restaurant finds out from a Stripe payout that doesn't
match its takings, weeks later. Same shape for the AR pipeline (`ar-generation.ts`
failures), for the R2 cleanup path (`uploads.ts:126,137`), and for the health
check (`api/health/route.ts:9`).

**Severity: P0** for a system that handles money unattended.

**Fix:** Sentry (or equivalent) via `instrumentation.ts`, ~30 minutes of work,
free tier is ample at this volume. Add a log driver to `docker-compose.yml` so
logs survive a container restart. Alert on: any webhook 500, any health-check
failure, and any `markOrderPaid` returning `ok: false`.

### P0-3 — No automated database backups

**Where:** `docker-compose.yml:90-91` — a named volume `postgres-data`. The
README documents a manual `docker compose exec postgres pg_dump …`. Nothing runs
it on a schedule; nothing ships it off the host.

**What is in that volume:** every order and its line items, the menu, the tables
and their numbers (which are printed on physical cards), and the only admin
account. **What is not:** dish photos and AR models, which correctly live in R2
(`src/lib/r2.ts`) and are the one part of the data that *is* durable.

A VPS disk failure, a bad `docker volume prune`, or a `migrate deploy` that goes
wrong currently loses the restaurant's entire menu and order history with no
recovery path.

**Severity: P0.** Lowest effort of the four blockers and the highest downside.

**Fix:** a `pg_dump` sidecar or host cron writing a daily dump to R2 (the
credentials and bucket already exist), with 30-day retention. Then **restore it
once into a scratch database** — an untested backup is not a backup.

### P0-4 — Placeholder business data and a default admin password

**Where:**
- `src/lib/constants.ts:7-23` — "123 Kabul Street, San Francisco, CA 94103",
  `+1 (555) 010-0100`, `hello@bagh-e-kabul.com`, and social links pointing at
  `https://instagram.com` / `https://facebook.com` (the sites' front pages).
  These render on the public site's footer, contact page, and map embed.
- `.env` — `ADMIN_PASSWORD` is still the documented default `ChangeMe123!`, and
  `SESSION_SECRET` **appears twice in the same file** with two different values,
  one of them prefixed `dev-`.

**Why it matters:** the seed script upserts the admin account from
`ADMIN_EMAIL` / `ADMIN_PASSWORD`. If `.env.production` is created by copying
`.env` — which is the natural thing to do and what the README's flow invites —
the live admin panel ships with a publicly documented password, and the panel is
reachable at a guessable path with a 10-attempts-per-15-minutes limit that a
known password walks straight through. The duplicated `SESSION_SECRET` is a
second, quieter hazard: it is not obvious which value actually signs sessions, so
"rotate the secret" cannot be done confidently.

`.env` is correctly gitignored (`.gitignore:34`) and correctly excluded from the
image (`.dockerignore:10-12`), so nothing is leaked — this is a launch-checklist
failure, not a breach.

**Severity: P0 as a launch gate.** Zero engineering, pure diligence.

**Fix:** real business details in `constants.ts`; a generated password and a
single generated `SESSION_SECRET` in `.env.production`; delete the duplicate line
from `.env`. Add a pre-launch checklist to the README so this can't be forgotten
under pressure.

### P1-5 — Unauthenticated Stripe API amplification on the confirmation page

**Where:** `src/app/(site)/checkout/success/page.tsx:33-45`.

```ts
if (orderId && sessionId && stripe) {
  const session = await stripe.checkout.sessions.retrieve(sessionId);
```

**The scenario:** `GET /checkout/success?orderId=x&session_id=anything` is
public, unauthenticated, and un-rate-limited (the limiter in `api-limits.ts`
guards `/api/*` routes only, not pages). Every request makes one outbound call to
Stripe's API. A trivial loop from one machine drives the account toward Stripe's
API rate limit; once there, **real checkouts start failing**, because
`POST /api/checkout/session` shares that budget.

The reconciliation logic itself is sound — `markOrderPaid` verifies the session
id against the stored order and compares the amount
(`order-payments.ts:35-40`), so a borrowed session id confirms nothing. The
problem is purely the unbounded outbound call.

**Severity: P1** — remotely triggerable, degrades the revenue path, cheap to
exploit.

**Fix:** skip the Stripe call entirely when it cannot help. Load the order first;
only call Stripe when the order exists, is `CARD`, is not already `PAID`, and the
supplied `session_id` matches the stored `stripeSessionId`. That reduces the
attack to "requests that name a real unpaid order the attacker already knows the
id of", which the webhook resolves anyway. Code in §6.

### P1-6 — AR generation can wedge permanently, with no way out from the UI

**Where:** `src/lib/ar-generation.ts:101-131` and
`src/app/api/dishes/[id]/ar-generate/route.ts:85-87`.

`dish.arGenerationTaskId` is cleared in exactly two places: `fail()` (line 84),
reached only when Meshy *reports* `FAILED` or `CANCELED`, and the success path
(line 161). If `getTask` throws for any other reason — Meshy unreachable, a 5xx,
an expired task id returning 404 — the exception propagates out of `advance()`,
the route returns 500 (`ar-generate/route.ts:114-116`), and the task id stays
set. From then on:

- `POST` short-circuits at line 85-87 and returns `{ status: "IN_PROGRESS" }`.
- `GET` throws again on every poll.
- `src/components/admin/ARModelUploader.tsx` has no reset control (verified by
  search: no reset/clear affordance exists).

The dish can never be regenerated. This was already identified as P1 in the
project's own `docs/AUDIT-PROMPT.md` (dated 2 August 2026) and is still open.

**Severity: P1.** Not on the money path — it degrades the product's
differentiator and the only remedy today is a manual database edit.

**Fix:** two small changes. Store a `arGenerationStartedAt` timestamp and treat a
task older than ~30 minutes as abandoned; and add a "Reset" button behind
`DELETE /api/dishes/[id]/ar-generate` that nulls the three `ar*` columns.

### P1-7 — Deleting a dish or a category orphans its R2 objects forever

**Where:** `src/app/api/dishes/[id]/route.ts:44-53` and
`src/app/api/categories/[id]/route.ts:28-46`.

```ts
const { id } = await params;
await prisma.dish.delete({ where: { id } });
return NextResponse.json({ success: true });
```

No call to `deleteUpload()` — even though the function exists, works for both R2
and legacy local files (`src/lib/uploads.ts:116-139`), and *is* correctly called
on every replace path (`dishes/[id]/image/route.ts:53`,
`categories/[id]/image/route.ts:53`, `ar-generation.ts:170`). Delete is the one
path that forgets.

**Cost:** a dish photo is up to 5MB; an AR model after re-encoding is measured in
tens of MB (`nginx/conf.d/default.conf:33` sizes the upload limit at 35MB). Every
deleted dish leaks both, permanently, with nothing to reconcile them against —
`scripts/fix-ar-models.ts` sweeps unreferenced *AR* files but there is no
equivalent for images.

**Severity: P1** — silent, monotonic, and it grows for the life of the product.

**Fix:** read the row before deleting, delete the row, then best-effort
`deleteUpload` both URLs. Code in §6.

### P1-8 — No idempotency on order submission

**Where:** `src/components/checkout/CheckoutForm.tsx:96` sets `submitting` before
the fetch — a client-side guard only. `POST /api/orders` has no idempotency key
and no duplicate detection.

**The scenario:** a diner on restaurant WiFi taps "Place order", the request
reaches the server and commits, the response is lost on the way back. The form
shows an error, they tap again. Two identical orders; the kitchen cooks both. For
cash dine-in this is worse than for delivery, because there is no name or phone
to call and reconcile with — the table is the only identity, and now it has two
tickets.

The per-table budget (10 per 15 min, `api-limits.ts:32`) bounds how bad this gets
but does nothing to prevent the double itself.

**Severity: P1** for a dine-in-first product. Costs real food.

**Fix, cheapest version:** have the client generate a UUID per checkout attempt
and send it as `Idempotency-Key`; store it in a unique column on `Order` and
return the existing order on conflict. **Cheaper still, if that's too much for
now:** on the server, reject a new order whose `tableNumber` + item set + total
matches one created in the last 60 seconds. Not airtight, but it removes the
common case for one migration and ~10 lines.

### P1-9 — No Content-Security-Policy

**Where:** `next.config.ts:6-18` sets HSTS, `X-Content-Type-Options`,
`X-Frame-Options`, and `Referrer-Policy` — a good baseline, correctly added — but
no CSP. Nothing in `nginx/conf.d/default.conf` adds one either.

**Calibration, honestly:** the exposure here is moderate, not severe. Card data
never touches this site (Stripe Checkout is a hosted redirect), React escapes
output by default, and there is no user-generated HTML rendered anywhere. CSP
here is defence-in-depth against a future XSS, and against a compromised
dependency exfiltrating the admin session cookie.

**Severity: P1**, mostly because it is genuinely cheap and gets harder to
retrofit as the app grows.

**Fix:** start in `Content-Security-Policy-Report-Only` mode to find what breaks
(`@google/model-viewer`, the Google Maps embed in `constants.ts:17`, and inline
styles from Tailwind are the likely candidates), then enforce.

### P2-10 — Dead API surface, one piece of it unbounded

Nothing in the application calls any of these (verified by searching every
`fetch` call site in `src/`):

| Route | Note |
| --- | --- |
| `GET /api/orders` (`api/orders/route.ts:71-89`) | **unbounded** `findMany` with `include: { items: true }` and no `take` — one request re-serialises the entire order history |
| `GET /api/dishes` (`api/dishes/route.ts:7-22`) | public, unused |
| `GET /api/dishes/[id]` (`api/dishes/[id]/route.ts:9-19`) | public, unused |
| `GET /api/categories` (`api/categories/route.ts:6-12`) | public, unused |

The admin *pages* correctly cap their own queries
(`admin/(protected)/orders/page.tsx:40-45`, `take: 100`, with a comment
explaining exactly why). The API route never got the same treatment because
nothing exercises it.

**Severity: P2** — an admin-authenticated endpoint, so the memory-pressure risk
requires a logged-in caller. But it is a live endpoint whose cost grows for ever.

**Fix:** delete all four handlers. If any is wanted later as a public menu API,
it comes back with pagination and a considered contract.

### P2-11 — The menu, the hottest path, has no caching

Every public page is `export const dynamic = "force-dynamic"` — `menu/page.tsx:9`,
`menu/[categorySlug]/page.tsx:13`, `dish/[slug]/page.tsx:18`. So every menu view
runs `category.findMany` + a full `dish.findMany` with `include: { category: true }`
(`menu/page.tsx:28-41`) and serialises the entire dish list into the RSC payload
to feed client-side search (`menu/page.tsx:45-52`).

**Calibrated:** for one restaurant this is fine. Postgres will serve this
thousands of times a second and the numbers do not lie about it. Two things make
it worth listing anyway: a QR-code product produces *correlated* load — a table
of six scans within seconds of each other, and a full dining room turning over
does this all evening — and the payload is being pushed over restaurant WiFi to
phones, where it is the user-visible cost.

`force-dynamic` on `/menu` is partly forced by reading `?table=`, but the dish
and category lists change perhaps weekly.

**Severity: P2.** Do not fix this before the P0s.

**Fix when convenient:** wrap the two menu queries in `unstable_cache` with a tag,
and revalidate that tag from the dish/category mutation routes. The `?table=`
lookup stays dynamic.

### What is genuinely good — and should not be touched

Stated plainly because a list of problems misrepresents this codebase:

- **Money handling.** Server-side re-pricing (`orders.ts:67-82`), the
  webhook/confirmation-page reconciliation split with amount and session-id
  verification (`order-payments.ts:26-61`), the compensating cancel when Stripe
  session creation fails (`checkout/session/route.ts:107-119`), and the
  deliberate decision *not* to publish an order event before payment lands
  (`checkout/session/route.ts:121-124`). This is better than most funded
  startups' checkout code.
- **The public/private data boundary.** `PUBLIC_ORDER_SELECT` as an explicit
  allow-list (`order-tracking.ts:18-36`), the admin SSE stream carrying literally
  no order data (`admin/orders/stream/route.ts:7-18`), and the awareness that RSC
  payloads are client-visible (`checkout/success/page.tsx:47-57`). Rare and
  correct.
- **Rate limiting keyed by table rather than IP for dine-in**
  (`api-limits.ts:68-100`), and charging the budget only *after* the table is
  proven real. Both come from thinking about how a restaurant's network actually
  looks.
- **Soft-deleting tables so a printed QR code can never be repointed**
  (`tables/[id]/route.ts:39-54`, `schema.prisma` `Table`). A genuinely
  physical-world-aware design decision.
- **The comments.** They explain *why*, cite the incident that motivated the
  code, and record what was verified and how. `next.config.ts:33-41` on why
  `remotePatterns` cannot read an env var is a small masterclass. Do not let a
  cleanup pass strip these.
- **The SSE implementation.** Unsubscribe on abort, heartbeats, connection cap,
  client-side close on terminal state, periodic resync as a safety net
  (`orders/[id]/stream/route.ts`). Correct on every detail that usually leaks
  sockets.

## 5. Refactor strategy

No rewrite. Nothing found justifies one — the architecture is sound and the
defects are additive gaps, not structural rot. Sequenced by risk-adjusted payoff:

### Phase 0 — Launch gate (days, not weeks). Do not go live without these.

1. **Real business data** in `src/lib/constants.ts`; delete the duplicate
   `SESSION_SECRET` from `.env`; generate a fresh admin password and session
   secret for `.env.production`. *(P0-4 — hours)*
2. **Automated `pg_dump` to R2**, daily, 30-day retention — **and one verified
   restore into a scratch database.** *(P0-3 — half a day)*
3. **Sentry via `instrumentation.ts`**, plus a log driver in
   `docker-compose.yml`. Alert on webhook 500s, health-check failures, and
   `markOrderPaid` returning `ok: false`. *(P0-2 — half a day)*

Zero risk, all three are additive, and together they turn "we hope nothing breaks"
into "we will know when something breaks."

### Phase 1 — Make the invariants defended (1–2 weeks, and the highest-value work here)

4. **Unit tests for the pure domain modules** — `order-state.ts`,
   `order-tracking.ts`, `table-qr.ts`, `validators.ts`. These need no database
   and no mocks, and they cover most of the rules the README treats as
   guarantees. Start here because the payoff/effort ratio is not close.
5. **Integration tests** for `buildOrderFromCart` and `order-payments.ts`
   against the existing dev Postgres container.
6. **`npm test` in CI**, gating merges alongside the existing typecheck/lint/build.

### Phase 2 — Close the exploitable and the leaky (days, low risk, all local)

7. Gate the Stripe call on `/checkout/success` *(P1-5)*.
8. Clean up R2 objects on dish/category delete *(P1-7)*.
9. Add an AR reset path + staleness timeout *(P1-6)*.
10. Order idempotency *(P1-8)* — do the simple version first.
11. Delete the four dead GET handlers *(P2-10)*.

Each is independently shippable and independently revertible. By this point every
one is covered by a Phase 1 test.

### Phase 3 — Polish, only once the above is done

12. CSP in report-only, then enforce *(P1-9)*.
13. Cache the menu queries with tag-based revalidation *(P2-11)*.
14. Sweep the P2-12 items: cart cap, `inFlight` on `globalThis`, `P2025` handling,
    dead upload code, the nginx `Connection` map, body caps on admin routes.

### Deliberately leave alone — and why

- **The per-process architecture** (rate limiter, SSE bus, AR lock). It is
  correct for one restaurant, and every one of the three modules documents the
  constraint. Introducing Redis now buys nothing and adds a service to operate.
  Revisit *only* when a second restaurant is real.
- **RSC pages querying Prisma directly.** Idiomatic and readable. A repository
  layer here would be indirection with no consumer.
- **The `globalThis` pinning pattern.** It looks like a smell and is a
  hard-earned fix for real Next.js bundling behaviour, documented at each site.
  Leave it — and make `ar-generation.ts` match it.
- **The comment density.** Above normal, and earning its keep. Resist any
  "clean up the comments" instinct.
- **SQLite→Postgres history squashed into one `init` migration.** Fine
  pre-launch. It stops being fine the moment there is production data.

### 6.1 — Stripe amplification on the confirmation page (P1-5)

**Before** — `src/app/(site)/checkout/success/page.tsx:33-45`, one unauthenticated
outbound Stripe call per page view:

```ts
if (orderId && sessionId && stripe) {
  try {
    const session = await stripe.checkout.sessions.retrieve(sessionId);
    if (session.payment_status === "paid") {
      await markOrderPaid(orderId, {
        sessionId: session.id,
        amountTotal: session.amount_total,
      });
    }
  } catch (error) {
    console.error("Could not reconcile checkout session", sessionId, error);
  }
}

const order = orderId
  ? await prisma.order.findUnique({ where: { id: orderId }, select: PUBLIC_ORDER_SELECT })
  : null;
```

**After** — load the order first and let it authorise the call. A `session_id`
that does not match the one already stored on the order buys nothing, so it never
reaches Stripe:

```ts
// Load first: the stored order is what decides whether calling Stripe can
// possibly help. Previously any stranger's `?session_id=` produced an outbound
// API call, so a loop against this public page could exhaust the account's
// Stripe rate limit and take real checkouts down with it.
let order = orderId
  ? await prisma.order.findUnique({
      where: { id: orderId },
      select: { ...PUBLIC_ORDER_SELECT, stripeSessionId: true },
    })
  : null;

const needsReconciliation =
  order !== null &&
  stripe !== null &&
  order.paymentMethod === "CARD" &&
  order.paymentStatus !== "PAID" &&
  // The id must be the one we handed Stripe ourselves. markOrderPaid checks
  // this too, but checking here is what keeps the network call off the
  // unauthenticated path in the first place.
  sessionId !== undefined &&
  order.stripeSessionId === sessionId;

if (needsReconciliation) {
  try {
    const session = await stripe!.checkout.sessions.retrieve(sessionId!);
    if (session.payment_status === "paid") {
      const result = await markOrderPaid(order!.id, {
        sessionId: session.id,
        amountTotal: session.amount_total,
      });
      // Re-read only when something actually changed, so the page renders the
      // state the customer just paid for rather than the one it loaded with.
      if (result.ok && result.changed) {
        order = await prisma.order.findUnique({
          where: { id: order!.id },
          select: { ...PUBLIC_ORDER_SELECT, stripeSessionId: true },
        });
      }
    }
  } catch (error) {
    // A Stripe outage must not stop the customer seeing the order they placed.
    console.error("Could not reconcile checkout session", sessionId, error);
  }
}
```

> Note: `stripeSessionId` is added to the *query*, not to the rendered output —
> keep passing only `PUBLIC_ORDER_SELECT` fields to `OrderTracker`, or destructure
> it away before rendering. That field must never reach the RSC payload
> (`order-tracking.ts:14-17`).

### 6.2 — Orphaned R2 objects on delete (P1-7)

**Before** — `src/app/api/dishes/[id]/route.ts:44-53`:

```ts
export async function DELETE(_request: NextRequest, { params }: Params) {
  const admin = await getAdminSession();
  if (!admin) {
    return NextResponse.json({ error: "Unauthorized" }, { status: 401 });
  }

  const { id } = await params;
  await prisma.dish.delete({ where: { id } });
  return NextResponse.json({ success: true });
}
```

**After** — read, delete, then best-effort clean up both assets. Same shape as the
existing replace paths (`dishes/[id]/image/route.ts:53`), so it needs no new
concepts:

```ts
export async function DELETE(_request: NextRequest, { params }: Params) {
  const admin = await getAdminSession();
  if (!admin) {
    return NextResponse.json({ error: "Unauthorized" }, { status: 401 });
  }

  const { id } = await params;

  // Read the asset URLs before the row goes: afterwards there is nothing left
  // pointing at them, and no sweep reconciles dish images against the bucket.
  // Every other path that replaces an asset already calls deleteUpload; delete
  // was the one that didn't, so each removed dish leaked its photo (up to 5MB)
  // and its AR model (tens of MB) permanently.
  const dish = await prisma.dish.findUnique({
    where: { id },
    select: { imageUrl: true, arModelGlbUrl: true },
  });
  if (!dish) {
    return NextResponse.json({ error: "Dish not found" }, { status: 404 });
  }

  try {
    await prisma.dish.delete({ where: { id } });
  } catch (error) {
    // P2025: another admin deleted it between the read and the write.
    if (
      error instanceof Prisma.PrismaClientKnownRequestError &&
      error.code === "P2025"
    ) {
      return NextResponse.json({ error: "Dish not found" }, { status: 404 });
    }
    throw error;
  }

  // After the row is gone, so a storage outage cannot block the delete the
  // admin asked for. deleteUpload already swallows and logs its own failures.
  await Promise.all([deleteUpload(dish.imageUrl), deleteUpload(dish.arModelGlbUrl)]);

  return NextResponse.json({ success: true });
}
```

Apply the identical shape to `categories/[id]/route.ts` for `category.imageUrl`.

## 7. Production-readiness roadmap

Assessed against what **a single-restaurant, pre-revenue, owner-operated product
at launch** actually needs. Where a domain's usual due-diligence expectations do
not apply at this stage, that is said rather than padded.

### 7.1 Code quality and architecture — **Strong**

Clear layering, consistent conventions, exceptional comment discipline, no `any`,
no TODOs, no dead-obvious duplication (the near-duplicate order-creation blocks in
`api/orders/route.ts:37-52` and `api/checkout/session/route.ts:42-57` differ only
in payment method and are legitimately clearer written out twice than
parameterised).

**Biggest gap:** none that blocks launch.
**Next step:** move `inFlight` onto `globalThis` so the codebase follows its own
documented rule everywhere *(P2-12b)*.

### 7.2 Security and compliance — **Good mechanics, weak hygiene**

Auth is correctly implemented rather than merely present: bcrypt, `jose`-signed
HttpOnly cookies, a `Secure` flag derived from `X-Forwarded-Proto` rather than
`NODE_ENV` (`auth.ts:13-26`), `SameSite=Lax` giving effective CSRF protection for
the JSON-body mutation routes, every `/api` handler individually authorised, and
`src/proxy.ts` guarding admin pages. Input validation is thorough, injection risk
is near-zero via Prisma, path traversal is guarded in both remaining file paths
(`uploads.ts:81-87`, `ar-generate/route.ts:27-30`), and secrets are properly kept
out of both git and the image.

**Biggest gap:** the default admin password and duplicated session secret in
`.env` *(P0-4)*, followed by the absence of a CSP *(P1-9)*.
**Unassessed:** dependency CVE exposure — `npm audit` could not reach the registry
from the audit environment. **Run `npm audit` and enable Dependabot before
launch.**
**Compliance:** PCI is out of scope (hosted Stripe Checkout, no card data
touches this code) — a genuine architectural win. GDPR/CCPA depends on
jurisdiction, which the code contradicts itself about (§2). **If the restaurant is
in the EU, a privacy policy and a retention policy for `customerEmail` /
`customerPhone` / `deliveryAddress` are legally required, and France additionally
requires *mentions légales*.** Neither exists today *(P2-12h)*. If it is in the
US, this is a should, not a must, at this scale.
**Next step:** rotate credentials, run `npm audit`, then resolve the jurisdiction
question — it is the one open item with legal rather than technical consequences.

### 7.3 Infrastructure and DevOps — **Good, one hole**

Well beyond typical MVP: multi-stage Dockerfile with a non-root user
(`Dockerfile:37-38,63`), health checks on both app and Postgres, dependency
ordering via `service_healthy`, migrations applied by the entrypoint with a
retry loop (`docker/docker-entrypoint.sh:12-22`), automated Let's Encrypt with —
notably — an nginx reload loop that fixes the classic "renewed but still serving
the expired cert" failure (`docker-compose.yml:64-71`). CI checks typecheck,
lint, build, **and** the Docker build.

**Biggest gap:** deployment is manual (`docker compose up -d` over SSH), there is
no staging environment, and rollback means rebuilding from a previous commit —
the image is tagged `:latest` only (`docker-compose.yml:27`).
**Next step:** tag images with the commit SHA so a rollback is a one-line compose
edit rather than a rebuild. Staging is genuinely optional at one restaurant;
image tagging is not.

### 7.4 Data architecture and database performance — **Good schema, no safety net**

The schema is well-designed for its access patterns: snapshot columns on
`OrderItem` so history survives menu edits, `tableNumber` as a plain int
deliberately *not* an FK so history survives table retirement, nullable contact
columns matching the dine-in rule, and — unusually — **explicit indexes on the
foreign keys and on the exact query shapes the admin screens use**
(`schema.prisma`: `@@index([createdAt])`, `@@index([status, createdAt])`,
`@@index([categoryId])`, `@@index([orderId])`). No N+1 patterns were found:
the dashboard runs five queries in one `Promise.all`
(`admin/(protected)/page.tsx:15-46`) and list pages use `include` rather than
per-row queries.

**Biggest gap:** no backups *(P0-3)*. Secondarily, the entire history is squashed
into one `init` migration — fine now, unacceptable once there is production data.
**Next step:** automated `pg_dump` to R2 **with a verified restore**. One minor
optimisation for later: the dashboard's `include: { items: true }`
(`admin/(protected)/page.tsx:31`) is used only for `items.length` — a `_count`
would do.

### 7.5 API design and integrations — **Consistent, with dead surface**

Conventions are followed uniformly: resource-shaped routes, correct status codes
(409 for illegal transitions and for the paid-order delete guard, 413 for
oversized bodies, 429 with `Retry-After`, 503 for unconfigured integrations), Zod
at every boundary, error messages written for a customer rather than a
stack trace. Third-party resilience is thought through: Stripe absent →
cash-only rather than broken; Meshy absent → AR silently unavailable rather than
crashed; R2 absent → an explicit named-variable error. Webhook retry semantics
are handled properly (`stripe/webhook/route.ts:30-37`).

**Biggest gap:** four unused GET handlers, one of them unbounded *(P2-10)*.
Versioning is correctly absent — a single-client API doesn't need it yet.
**Missing:** no timeouts on outbound `fetch` to Meshy (`meshy.ts:42`) or on the
model download (`ar-generation.ts:49`). A hung connection ties up a request
indefinitely.
**Next step:** delete the dead handlers; add an `AbortSignal.timeout()` to both
outbound fetches.

### 7.6 Application performance — **Adequate for scale, unmeasured**

The known heavy paths are already bounded — admin orders capped at 100 with the
reasoning written down, SSE connections capped at 200, request bodies capped,
order items capped at 50 after a real incident. Nothing found will strain a
single restaurant.

**Biggest gap:** there is no measurement of any kind — no load test, no APM, no
performance budget. Every performance claim here (mine and the README's) is
reasoning, not observation.
**Next step:** the Sentry install from §5 gives basic transaction timing for free.
A one-off load test simulating one dining room's worth of simultaneous menu loads
would confirm or refute finding P2-11 in an afternoon. Neither is a launch
blocker.

### 7.7 Technology stack and dependencies — **Modern, lean, appropriately boring**

24 production dependencies, all mainstream and maintained, no abandoned packages,
no framework at end-of-life. Next.js 16 + React 19 + Prisma 7 + Tailwind 4 is
current. Prisma's `driver-adapter` path is the modern one. The stack is
well-matched to a very small team, and the deliberate rejection of serverless in
favour of one persistent container (`README.md` → "Deploying") is correct
reasoning given in-process SSE and rate limiting.

**Biggest gap:** running the newest major of everything means being on the
bleeding edge of each — `AGENTS.md` exists precisely because Next 16's APIs
differ from what's widely documented. That is a maintenance tax to accept
knowingly, not a mistake. **Unassessed:** CVE exposure (see §7.2).
**Next step:** `npm audit` + Dependabot with weekly grouped PRs.

### 7.8 Testing and QA — **Absent. The single largest gap in the project.**

Zero automated tests. Zero coverage on every critical path identified in §3.
CI's four checks confirm the code compiles and the image builds — not that a
single business rule holds. The manual QA that exists is real and unusually
disciplined (`docs/AUDIT-PROMPT.md` is a serious structured review process, and
its "never physically verified" section is exactly the right kind of honesty),
but it is human, sequential, and does not run on every commit.

**Biggest gap:** everything.
**Next step:** §6.3, verbatim. An hour of work covers most of the rules the
README treats as guarantees, and it is the difference between "these invariants
hold" and "these invariants held the last time someone checked by hand."
